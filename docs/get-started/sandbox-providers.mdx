---
title: Configure sandbox providers
description: Store sandbox-provider credentials and select a provider for runs.
---

Valkyrie resolves sandbox-provider credentials from AWS Secrets Manager; a [local Tracker](/self-hosting/local-tracker) can read them from a `.env` file instead. Store them with [`valkyrie secret set`](/reference/cli/secret#set), which prints the reference to use, then map a provider name to that secret with [`valkyrie provider set`](/reference/cli/provider#set). The Tracker keeps the mapping for your organization, so every member's runs on that provider use it. The secret has to exist in your organization's secrets first; a self-hosted Tracker without authentication can map the name of a secret created directly in AWS. Full syntax is in the [`provider set`](/reference/cli/provider#set), [`provider list`](/reference/cli/provider#list), and [`provider default`](/reference/cli/provider#default) reference.

## Select a provider

A run uses the provider you pass with `--provider`, otherwise your default provider, otherwise `daytona`. Choose your own default with:

```bash
valkyrie provider default daytona
```

The default is yours alone in the current organization; it does not change what other members run on. `valkyrie provider list` shows each provider's secret and marks your default.

Select a provider for one run:

```bash
valkyrie run start --agent sweagent --benchmark swebench --provider daytona
```

Provider secret schemas are provider-specific. Mapping a name does not make one provider's secret shape valid for another provider.

## Daytona

1. [Create a Daytona API key](https://app.daytona.io/dashboard/keys) with read, write, and delete access to sandboxes and snapshots.
2. Choose a target from Daytona's [shared regions](https://www.daytona.io/docs/regions#shared-regions).
3. Store the following JSON as a secret, for example with `valkyrie secret set daytona < daytona.json`:

   ```json
   {
     "DAYTONA_API_KEY": "...",
     "DAYTONA_API_URL": "https://app.daytona.io/api",
     "DAYTONA_TARGET": "..."
   }
   ```

Map the provider to the secret by the name `secret set` printed:

```bash
valkyrie provider set daytona daytona
```

## Modal

1. [Create an API token](https://modal.com/docs/reference/modal.config#authentication) under `Settings → Tokens → API tokens`, in the Modal workspace that should own the sandboxes. Modal shows the token once, as a CLI command:

   ```bash
   modal token set --token-id ak-... --token-secret as-...
   ```

2. Store the token id and secret from that command as a secret, for example with `valkyrie secret set modal < modal.json`:

   ```json
   {
     "MODAL_TOKEN_ID": "ak-...",
     "MODAL_TOKEN_SECRET": "as-..."
   }
   ```

Map the secret to the provider `modal`:

```bash
valkyrie provider set modal modal
```

The provider name is sent to the benchmark service as the provider type, so Modal credentials must be mapped under `modal`.

<Note>
  Modal support comes from the benchmark service, not the CLI. The service must pin `create-benchmark-service` `v0.14.0` or later; earlier releases fail the run with `Modal sandbox provider is not implemented`.
</Note>
