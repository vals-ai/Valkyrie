Each method's parameters, defaults, and return types are in the [`client.runs` reference](/reference/sdk/runs#start).

## Start a run

Use an uploaded agent name or an `AgentContractRequest`:

```python
run = await client.runs.start(
    agent="sweagent",
    benchmark="swebench",
    model="anthropic/claude-sonnet-4-6",
    concurrency=10,
    priority=3,
    dataset="default",
    label="nightly-swebench",
)
```

`priority` accepts `0` (P0, highest) through `4` (P4, lowest). Managed shared-pool runs default to P3 when it is omitted. An explicit priority is rejected when the tracker queue is disabled or the selected provider uses direct execution. See [Start a run](/runs/start#prioritize-work-in-a-managed-sandbox-pool) for the queue behavior.

## Select managed run storage

Use `managed_s3_bucket` for a bucket that your application has provisioned and tagged for your Valkyrie organization:

```python
from valkyrie.sdk import ValkyrieRunAcceptedError, ValkyrieRunError

try:
    run = await client.runs.start(
        agent="sweagent",
        benchmark="swebench",
        managed_s3_bucket="vs-dev-acme-123",
    )
except ValkyrieRunAcceptedError as error:
    # The run exists in the requested bucket. Reconcile or retry it by this ID.
    await reconcile_run(error.run_id)
    raise
except ValkyrieRunError as error:
    # The bucket was rejected. Quarantine the run; do not start it again.
    await record_storage_rejection(error.run_id)
    raise

actual_bucket = run.storage_bucket
```

Catch `ValkyrieRunAcceptedError` before `ValkyrieRunError`. Both carry a `run_id`, so the ID alone does not tell the two outcomes apart:

- `ValkyrieRunAcceptedError` means the run was created with the bucket you asked for, and only its executor dispatch went unacknowledged. The storage is correct, so reconcile or retry by `run_id`. The original `ValkyrieAPIError` is the cause.
- Plain `ValkyrieRunError` means the start response carried a missing or different `storage_bucket`. That is a storage rejection. Do not submit it again without an explicit override.

A caller that catches only `ValkyrieRunError` still sees both, so an older handler keeps working, but it cannot separate them and will quarantine correctly stored runs.

The SDK uses `/start-benchmark-with-storage`. An older tracker returns 404 before it creates a run. Do not retry on `/start-benchmark` or remove the bucket after an error. Existing message-only error construction remains supported and gives `run_id=None`.

The override cannot be combined with access-key credentials or explicit `properties`. The tracker checks the bucket account, region, organization tag, environment, and enabled versioning. Agent-library reads remain in shared storage; the frozen bundle and run artifacts use the selected bucket. See [Managed run storage deployment](/deployment/managed-run-storage) for policy and rollout requirements.

Persist the returned `storage_bucket` for each run. `client.runs.fetch`, `client.runs.metadata`, streaming progress, and `client.benchmarks.fetch` also return the actual bucket. Saved resources remain authoritative after deployment defaults change and during retry or recovery. Legacy managed rows without saved resources use the shared deployment bucket until their first new recovery saves that location. Legacy access-key metadata without enough credentials returns `None`.

Artifact download URLs require no new HTTP header. Use the complete returned URL with an ordinary HTTP client.

## Fetch or stream progress

```python
current = await client.runs.fetch(run.benchmark_id)

async for update in client.runs.stream(run.benchmark_id):
    print(update.details.status)
```

## List, score, and recover runs

```python
page = await client.runs.list()
results = await client.runs.results(run.benchmark_id)
await client.runs.stop(run.benchmark_id)
await client.runs.resume(run.benchmark_id, concurrency=20)
await client.runs.retry(
    run.benchmark_id,
    task_ids=["task-1"],
    benchmark_url="https://new-benchmark.example",
)
```

Use `benchmark_url` when a benchmark service does not have a stable URL. `resume` picks up work that never ran, while `retry` re-runs tasks that ended in `ERROR`. See [Manage a run](/runs/manage) for the lifecycle rules that apply to both.

Fetch the stored launch metadata, or check whether the run's S3 results are there yet:

```python
metadata = await client.runs.metadata(run.benchmark_id)
exists = await client.runs.results_exist(run.benchmark_id)
```

## Analyze a completed run

Uncached analysis requires the analyzer Lambda name from the agent contract:

```python
async for event in client.runs.analyze(
    run.benchmark_id,
    lambda_function="my-agent-analyzer",
):
    print(event.event, event.data)
```

## Stream run outputs

Stream the tar archive without loading it all into memory:

```python
from pathlib import Path

with Path("run-outputs.tar").open("wb") as archive:
    async for chunk in client.runs.stream_outputs(run.benchmark_id):
        archive.write(chunk)
```

## Which executor release ran the work

A run response reports both the release it started on and the one running it now:

| Field | Meaning |
| --- | --- |
| `executor_release_id` | The release chosen when the run was first admitted, which never changes |
| `current_execution_release_id` | The release running the work now, which a retry or resume of a finished run can move forward |
| `executor_artifact_digest` | Digest of the artifact from that first release |
| `executor_protocol_version` | Protocol version of that first release |

Runs that predate these fields return `null` for all of them. The metadata endpoint also reports the first `executor_artifact_uri`, and each dispatch keeps its own snapshot of the exact artifact that invocation used.
