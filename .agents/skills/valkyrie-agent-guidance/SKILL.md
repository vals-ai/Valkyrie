# Valkyrie agent guidance

## Branch and scope

- Use `dev` as the base branch for Valkyrie work. Do not use `main` for code review, dependency checks, or PR bases.
- Prefer focused changes and update docs when adding or changing CLI options, API options, or deprecated behavior.
- Read `README.md` and relevant files under `docs/` before changing user-facing behavior.

## Local checks

- Run `make style` from the repo root for formatting and linting.
- Run `make typecheck` from the repo root when Python source changes touch the CLI package under `src/`.
- For tracker changes, prefer targeted tests. Use `cd services/tracker && uv run pytest <path>::<test>` when possible.
- Use `cd services/tracker && make test-unit` for broader tracker validation, especially after touching tracker models, migrations, lifecycle logic, auth, sandbox, or worker behavior.
- Do not run the full integration suite unless the change is broad enough to justify it or the user asks for it.

## Tracker service and API testing

- Start the tracker from the repo root with `make tracker-service`; health-check only with `curl http://localhost:8000/health`.
- Do not raw-curl tracker endpoints that require harness configuration unless you intentionally provide the needed headers. Most tracker API routes expect `X-Harness-*` headers generated by the CLI from `~/.config/valkyrie/valkyrie.yaml`.
- Prefer testing tracker workflows through `valk` / `valkyrie` commands so auth and harness headers match real usage.
- Always capture the run ID from `valk run start`; it is required for follow-up commands such as `fetch`, `stop`, `resume`, `retry`, `results`, and `agent outputs`.

## Hosted-mode tracker testing

- Hosted mode requires `AUTH_REQUIRED=true`, `DESCOPE_PROJECT_ID`, and usually `DESCOPE_MANAGEMENT_KEY` for local tracker attribution tests.
- Host environment variables do not automatically reach Docker containers. Confirm `services/tracker/docker-compose.yml` forwards required hosted-mode variables for both relevant services, then verify with:

```bash
docker exec tracker-service-container env | grep -E "AUTH_REQUIRED|DESCOPE"
docker exec tracker-worker-container env | grep -E "AUTH_REQUIRED|DESCOPE"
```

- If `/init` returns `405 "Init is only available in hosted mode"`, first verify the env vars reached the containers.
- `valk config service set` and related config commands rewrite `~/.config/valkyrie/valkyrie.yaml`; re-check the config after using them, especially when testing missing-auth behavior.
- If the default benchmark service is unreachable, ask for a reachable benchmark service IP/port and any required allowlisting before continuing benchmark start tests.

## Benchmark service and Docker networking

- `BENCHMARK_SERVICE_BASE_URL` makes tracker construct `https://<benchmark>.<base>`. Without it, tracker falls back to CloudMap-style `http://<benchmark>.local:8001`, which only works in the expected network.
- For local benchmark services, prefer `valk config service set <benchmark> <url>` and test through the CLI.
- When a tracker container must call a service on the host, use Docker-reachable hostnames or compose networking rather than assuming `localhost` inside the container points to the host.

## Sentry and observability

- Sentry events receive context tags from `request_id`, `benchmark_id`, and `task_id` context vars. Search Sentry by `benchmark_id:<uuid>` or `task_id:<id>` when investigating run or task failures.
- Sandbox and PTY failures may also be tagged with `sandbox_id`, `sandbox_name`, `sandbox_state`, `pty_session_id`, `pty_attempt`, `daytona.op`, and `error_class`.
- Prefer these tags over broad text search when triaging tracker-worker exceptions.

## Daytona and provider setup

- Daytona credentials are stored in AWS Secrets Manager under the configured `DAYTONA_SECRET_NAME` and must include `DAYTONA_API_KEY`, `DAYTONA_API_URL`, and `DAYTONA_TARGET`.
- Daytona API keys need sandbox and snapshot read/write/delete permissions.
- Provider or sandbox changes should preserve provider-agnostic tracker behavior; keep Daytona-specific setup isolated behind the provider/sandbox utilities.
- If changing sandbox lifecycle behavior, add or update targeted tracker tests around sandbox creation, command execution, PTY/session handling, artifact upload, and cleanup.
